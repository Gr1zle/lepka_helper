# Аватар и фотографии этапов — 29 октября 2026

Продолжение исправления интерфейса и завершения инструментов из плана. ТЗ, включая историческую дату сдачи 25.04.2026, не изменено. Загрузка аватара предусмотрена пунктом 4.1.7, фото этапов — пунктами 4.1.4.9 и 4.1.19.4.

## Почему аватар не отображался

Старый обработчик сохранял `selectedFile.path` или `selectedFile.name` и передавал эту строку элементу CircleAvatar. В браузере путь обычно отсутствует, а имя файла не даёт приложению доступа к его содержимому. Выбор файла открывался, но байты изображения не загружались. В режиме API выбор аватара вообще блокировался сообщением о недоступности серверной загрузки.

Теперь браузер загружает содержимое через уже используемый маршрут временных фотографий. Настольный режим читает выбранный файл. Общий компонент `photo_picker.py` проверяет сессию, тип и размер, обрабатывает отмену и ошибки; веб-режим определяется сервером и не позволяет подставлять пути файлов ПК. Изображение показывается через `ft.Image(src_base64=...)` внутри круглого аватара.

## Аватар

- JPG/JPEG, PNG и WebP до 10 МБ, максимум 20 мегапикселей. Формат проверяется по содержимому, анимация и повреждённые файлы отклоняются.
- Изображение автоматически обрезается по центру до 512 × 512 и круглой маски; сохраняется PNG с прозрачными углами, без EXIF/GPS. Интерактивного перемещения рамки кадрирования нет. Исходный файл не изменяется.
- Выбор фотографии сразу сохраняет аватар. Кнопка «Сохранить профиль» сохраняет остальные поля, не стирая изображение. «Убрать аватар» удаляет его и возвращает начальную букву имени.
- В локальном режиме байты находятся в новом поле `users.avatarImage` клиентской SQLite. В серверном режиме они хранятся в базе API; технический локальный аккаунт не получает чужие данные при совпадении числовых ID.
- `PUT /profile/avatar` принимает нормализованный PNG до 2 МБ и повторно обрабатывает его на сервере. Владелец берётся из Bearer-токена. `GET /profile` возвращает `avatarImage` в Base64, `DELETE /profile/avatar` удаляет изображение. Сервер не принимает путь файла устройства.
- Pillow добавлен в серверные зависимости и Docker-образ. Ключ Resend для аватара не используется; схема отправки писем не менялась.

Base64 здесь нужен для передачи байтов в JSON и элемент Flet. Это не ссылка на файл и не способ уменьшения размера изображения.

Старое поле `avatarPath` не удалено миграцией. Валидные старые пути сохраняют прежний настольный способ отображения. Одного сохранённого имени файла браузера недостаточно для восстановления фотографии: её нужно выбрать заново. Новый выбор или явное удаление очищает старый путь.

## Фотографии этапов

- У каждого этапа можно добавить одну фотографию, заменить её и посмотреть в карточке. Используется та же проверка JPG/PNG/WebP и размера, что для публикаций; изображение уменьшается до 1600 пикселей по большей стороне и хранится как JPEG без EXIF/GPS.
- Байты хранятся в `projectSteps.photoImage`. Признак `hasPhoto` позволяет строить список этапов без чтения всех изображений; само фото загружается отдельным запросом SQLite только для владельца соответствующего проекта и этапа.
- Фото приватны. В веб-версии они передаются только в контролы вошедшей сессии; публичный маршрут фотографий сообщества не обращается к таблице этапов.
- По пункту 4.1.19.4 фото необязательно при создании, но нужно при завершении. Проверка выполнена в сервисе и в условии SQL-обновления статуса, поэтому новая отметка без фото отклоняется и не увеличивает прогресс.
- У завершённого этапа фото можно заменить. Для удаления нужно сначала снять отметку выполнения. Это не позволяет оставить новый завершённый этап без изображения.
- Старые отметки выполнения при обновлении не сбрасываются. Старый завершённый этап без фото остаётся в данных и получает пояснение в интерфейсе; после снятия отметки повторное завершение уже требует фото. Наличие старой отметки не доказывает соответствие старой записи новому сценарию.
- Удаление этапа, проекта или аккаунта удаляет встроенные байты вместе с записью. Исходные файлы пользователя не удаляются. Подстановка чужого проекта, этапа или пользователя не даёт доступа к приватной фотографии.

Фото проектов по-прежнему локальные, включая режим серверных аккаунтов. Синхронизация проектов и их файлов не добавлена этим исправлением. Для личного этапа ТЗ требует фотографию; видео в этом пункте не заявлено. Фото/видеоуроки остаются отдельным открытым требованием.

## Проверки

- **151 тест, OK**: прежние 136 проверок и 15 новых. Проверены круглый PNG 512 × 512, сохранение после изменения других полей/повторного входа/инициализации, удаление, сохранность старых данных, права владельца, повреждённые и слишком большие файлы, обязательное фото при новой отметке и отказ удалить фото завершённого этапа.
- Прежние тесты прогресса получили фотографии в тестовых данных, чтобы проверять расчёт в корректном по ТЗ сценарии. Отдельные новые проверки подтверждают отказ без фотографии на уровне сервиса и SQL.
- HTTP API проверен на временной базе: токен обязателен, подстановка `userId` не меняет владельца, неверная загрузка сохраняет старый аватар, тело больше 2 МБ отклоняется, отозванная сессия не загружает изображение.
- Клиент Flet проверен с настоящим API в отдельном процессе: выбор аватара, серверное хранение, отображение, сохранение профиля без потери фото и удаление. Серверная и клиентская базы раздельные.
- Локальные проверки интерфейса явно изолированы от адреса API из пользовательского окружения. Полный прогон с `LEPKA_API_URL=https://example.invalid` также прошёл: локальные сценарии используют временную SQLite, интеграционные — собственные временные серверы.
- Новый Docker-образ собран. В отдельном контейнере проверены авторизация, PUT/GET аватара, повторный запуск с тем же временным томом и DELETE. Изображение сохранилось после перезапуска. Тестовые контейнер и том удалены; пользовательские данные не использовались.

Оба изображения просмотрены на скриншотах. Для статических ресурсов Flutter в облачном браузере использован Requests с проверкой TLS, как на предыдущем этапе.

## Проверка на своём компьютере

Переключиться на ветку `fix/avatar-stage-photos`. Сохранить копию существующей базы и использовать прежние папки данных, не создавая пустую базу вместо своей.

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Затем перезапустить **оба процесса**, если включён серверный режим:

1. Сервер API — прежней командой из `backend/README.md` и с тем же `LEPKA_SERVER_DATA_DIR`. При отдельном окружении сервера обновить его `backend/requirements.txt`. Для Docker пересобрать образ, сохранив прежний том `/data` и настройки запуска.
2. Клиент — `python main.py` из своего окружения. Адрес API оставить прежним; почтовые ключи клиенту не передавать.

Ручные сценарии:

1. «Профиль» → «Выбрать аватар»: выбрать фото, дождаться изображения в обоих кружках. Переключить вкладку, вернуться; изменить биографию и сохранить; выйти и войти — аватар остаётся.
2. Выбрать некорректный файл: прежний аватар сохраняется, появляется ошибка. «Убрать аватар» возвращает букву имени.
3. В тестовом проекте создать этап и попробовать завершить без фото: отметка отклоняется, прогресс не растёт.
4. «Добавить фото этапа» → дождаться превью → отметить выполнение. Проверить прогресс. Фото завершённого этапа можно заменить; удалить — после снятия отметки.
5. В другом аккаунте этот проект и его фото не видны. Удалить только специально созданный тестовый проект; исходные изображения на диске сохраняются.

## Дальнейшая очередь

Это исправление закрывает загрузку аватара из предыдущего аудита и часть пункта 32 — фото этапов. Изменение порядка этапов, JSON проектов, камера и напоминания ещё не сделаны.

В очереди остаются серверное сообщество и синхронизация, модерация комментариев с причиной и журналом, push, автодополнение тегов, избранное и привязка публикаций, полноценные челленджи, публичные профили авторов и 3D. Публичное HTTPS-размещение аккаунтов и мобильные испытания тоже открыты. Эти требования не исключаются из ТЗ и не считаются выполненными текущими фотографиями.
